# 08: "Frictionless Onboarding" vs. Dynamisches JavaScript

## Meta

Status
: Work in progress - **Decided** - Obsolete

Updated
: 23-Jun-2026

## Problem Statement

Bei der Registrierung wählen Nutzer ihre Rolle (Student oder Professor). Da Professor/innen einer bestimmten Facheinheit angehören, stand die Überlegung im Raum, das Dropdown für die `Facheinheit` direkt in das Registrierungsformular zu integrieren. 

Da dieses Feld jedoch für Studierende irrelevant ist, hätte es aus UX-Gründen mittels clientseitigem JavaScript (Event Listener) bei der Auswahl "Student" versteckt oder gesperrt werden müssen. Die Projektrichtlinien verbieten jedoch den Einsatz von Custom JavaScript (Forbidden Technology).

## Decision

Die Abfrage rollenspezifischer Daten (wie der Facheinheit) wird **aus dem Registrierungsprozess entfernt und in das Profil-Dashboard verschoben** (Frictionless Onboarding). 

Das Registrierungsformular enthält nun nur noch essenzielle Pflichtfelder (Name, E-Mail, Passwort, Rolle). Nach dem ersten Login leitet das System den Nutzer (via Session-Flag) direkt auf sein Profil, wo er die Facheinheit mittels Flask-WTF serverseitig sicher auswählen kann.

Diese Entscheidung stellt die 100%ige technische Compliance sicher (Verzicht auf JavaScript) und senkt zeitgleich die Einstiegshürde bei der Account-Erstellung signifikant.

## Regarded Options

| Kriterium | Abfrage in der Registrierung (mit JS) | Frictionless Onboarding (Auslagerung ins Profil) |
| :--- | :--- | :--- |
| **Compliance (Forbidden Tech)** | Verstoß (Custom JS erforderlich) | Konform (Rein serverseitig) |
| **Einstiegshürde Account-Erstellung**| Höher (mehr Felder) | Sehr niedrig |
| **Datensicherheit** | JS im Client manipulierbar | Backend-Validierung greift sauber |

### Belege und Artefakte
* Konsequenter Verzicht auf `<script>`-Tags in `templates/register.html`.
* Implementierung des Reverse Route-Guardings (`session['just_registered']`) in `app.py`.
