# 11: Secrets-Management — SECRET_KEY als Umgebungsvariable

## Meta

Status
: Work in progress - **Decided** - Obsolete

Updated
: 18-Jul-2026

## Problem Statement

Der Flask-`SECRET_KEY` signiert Session-Cookies und CSRF-Tokens. Bisher stand er als
Klartext-Literal in `app.py` und damit dauerhaft in der Git-Historie des Repositories.
Wer den Key kennt, kann beliebige Session-Cookies fälschen (z. B. mit der `user_id`
eines Professors) und die gesamte Authentifizierung umgehen — das Passwort-Hashing
aus DD-10 wäre damit wirkungslos.

## Decision

Der `SECRET_KEY` wird nicht mehr im Code gespeichert, sondern beim App-Start per
`python-dotenv` aus einer lokalen `.env`-Datei geladen, die über `.gitignore` vom
Repository ausgeschlossen ist. Fehlt die Variable, bricht die App sofort mit einem
`RuntimeError` und einer Handlungsanweisung ab (**Fail fast**) — ein unsicherer
Fallback-Key im Code hätte das ursprüngliche Problem nur versteckt. Eine committete
`.env.example` plus README-Schritt dokumentieren das Setup für das Team; jede
Umgebung generiert ihren eigenen Key (`secrets.token_hex(32)`). Da der alte Key in
der Git-Historie einsehbar bleibt, wurde er im Zuge der Umstellung **rotiert**.
Ergänzend wurden die Session-Cookies gehärtet (`SESSION_COOKIE_HTTPONLY`,
`SESSION_COOKIE_SAMESITE='Lax'`).

Entschieden im Team nach der mündlichen Abfrage; implementiert durch
Nikita Pasichnyk (`app.py`, `.env.example`, `.gitignore`, `README.md`).

## Regarded Options

| Kriterium | Hartkodiert im Code (Status quo) | Umgebungsvariable via `.env` (gewählt) | `os.environ.get()` mit Fallback-Default |
| :--- | :--- | :--- | :--- |
| **Sicherheit** | Key öffentlich in der Git-Historie | Key nur lokal, pro Umgebung eigener Wert (12-Factor-Prinzip „Config") | Unsicherer Default-Key läuft unbemerkt weiter |
| **Team-Setup** | Kein Aufwand | Ein dokumentierter Schritt (README, `.env.example`) | Kein Aufwand |
| **Fehlerverhalten** | — | Fail fast: Start bricht mit klarer Meldung ab | Fehlkonfiguration bleibt unsichtbar |
