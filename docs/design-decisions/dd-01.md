# 01: PDF-Anhänge — Datei im Upload-Ordner statt BLOB in der Datenbank

## Meta

Status
: Work in progress - **Decided** - Obsolete

Updated
: 23-Jun-2026

## Problem Statement

Studierende und Professor/innen sollen PDF-Dateien an Betreuungsanfragen bzw. Chat-Nachrichten anhängen können. Es muss entschieden werden, wie die Binärdatei gespeichert wird: direkt als BLOB in der SQLite-Datenbank oder als Datei im Dateisystem, wobei in der Datenbank nur die Metadaten (Originalname, Speicherpfad, Größe, MIME-Typ) abgelegt werden.

## Decision

Die PDF-Datei wird **im Upload-Ordner auf dem Dateisystem** gespeichert; in der Datenbank liegen nur die **Metadaten** (Tabelle `attachments`). Die Datei bekommt beim Speichern einen eindeutigen Namen (UUID), der Originalname wird für den Download in den Metadaten gehalten.

Aus meiner eigenen Erfahrung ist der BLOB-Ansatz nicht grundsätzlich schlecht: Für das Demo einer eigenen Startup-Idee habe ich bereits Fotos als BLOBs in der Datenbank gespeichert und an eine KI geschickt, damit daraus Tiefenkarten erstellt werden konnten. Das hat in dem Kontext einwandfrei funktioniert.

Für dieses Projekt überwog aber der Datei-Ansatz, weil:

+ das Datenmodell-Dokument ihn explizit vorgibt („Datei im Upload-Ordner, Metadaten in SQLite"),
+ PDFs die SQLite-Datei spürbar aufblähen würden — und da die DB bei uns im Git-Repo liegt und unser Setup anfangs etwas chaotisch war (häufige Merge-Konflikte auf der DB-Datei), hätten große BLOBs die Entwicklung zusätzlich erschwert,
+ das Ausliefern einer Datei direkt vom Dateisystem einfacher ist als aus einem DB-BLOB,
+ es dem Standard-Flask-Pattern entspricht (`UPLOAD_FOLDER`, `secure_filename`).

*Decision was taken by:* github.com/petrovvvic (Andrei Piatrouski)

## Regarded Options

Abgewogen wurden zwei Optionen:

+ Datei im Upload-Ordner + Metadaten in der DB (gewählt)
+ Datei als BLOB direkt in der Datenbank

| Kriterium | Datei + Metadaten | BLOB in der DB |
| --- | --- | --- |
| **DB-Größe** | bleibt klein | wächst stark (kritisch, da die DB im Repo liegt) |
| **Ausliefern** | direkt vom Dateisystem (`send_from_directory`) | Datei erst aus der DB lesen und zurückgeben |
| **Backups / Portabilität** | DB bleibt schlank | DB-Datei wird groß und unhandlich |
| **Standard-Pattern (Flask)** | entspricht der Doku | unüblich |
| **Eigene Erfahrung** | aus früherem Projekt bekannt (JSON-Dateien in S3, Metadaten in MongoDB) | hat für Fotos (an eine KI zur Tiefenkarten-Erstellung geschickt) im Startup-Demo gut funktioniert |

Beleg / Artefakt: umgesetzt in Commit [fb43b10](https://github.com/petrovvvic/team2_thesis_match/commit/fb43b10); die Metadaten-Struktur ist im Modell `Attachment` (`db.py`) und in der Tabelle `attachments` zu sehen.
