# 03: Gemeinsames rollenabhängiges Dashboard statt getrennter Dashboards

## Meta

Status
: Work in progress - **Decided** - Obsolete

Updated
: 23-Jun-2026

## Problem Statement

Studierende und Professorinnen beziehungsweise Professoren benötigen unterschiedliche Ansichten auf ihre Betreuungsanfragen.

Studierende sollen ausschließlich die von ihnen erstellten Anfragen sehen. Professorinnen und Professoren sollen ausschließlich die Anfragen sehen, die an sie gerichtet wurden.

Trotz dieser unterschiedlichen Daten und Funktionen haben beide Rollen einen gemeinsamen fachlichen Kontext. Beide arbeiten mit Betreuungsanfragen, Statuswerten und den jeweils beteiligten Personen.

Es musste daher entschieden werden, ob:

* für jede Rolle eine eigene Flask-Route und ein eigenes Template erstellt werden,
* eine gemeinsame Route und ein gemeinsames Template mit Rollenbedingungen verwendet werden oder
* eine gemeinsame Route mit mehreren getrennten Untertemplates umgesetzt wird.

## Decision

Für Studierende und Professorinnen beziehungsweise Professoren wird eine gemeinsame Route `/dashboard` und ein gemeinsames Template `dashboard.html` verwendet.

Die Route ermittelt zunächst den angemeldeten Benutzer. Anschließend wird abhängig von der Benutzerrolle eine unterschiedliche SQLAlchemy-Abfrage ausgeführt:

* Bei Studierenden werden Betreuungsanfragen über `student_id` gefiltert.
* Bei Professorinnen und Professoren werden Betreuungsanfragen über `professor_id` gefiltert.
* Für nicht unterstützte Rollen wird eine leere Ergebnismenge verwendet.

Die gefundenen Anfragen werden gemeinsam mit den Statuszählungen an dasselbe Jinja-Template übergeben.

Innerhalb des Templates werden rollenabhängige Texte, beteiligte Personen und Aktionen mithilfe von Jinja-Bedingungen dargestellt.

Diese Lösung wurde gewählt, weil:

* beide Rollen mit derselben Art von Datensätzen arbeiten,
* die gemeinsame Grundstruktur nicht doppelt gepflegt werden muss,
* Änderungen am Layout zentral durchgeführt werden können,
* rollenabhängige Daten bereits sicher in der Flask-Route gefiltert werden und
* der Umfang der Anwendung keine vollständig getrennten Dashboard-Architekturen erfordert.

Die Rollenbedingungen im Template dienen nur der Darstellung. Die Auswahl der zulässigen Datensätze und die Berechtigungsprüfungen erfolgen weiterhin serverseitig in der Flask-Anwendung.

Die Entscheidung wurde von Abdulhamid Suliman vorbereitet, umgesetzt und dokumentiert.

## Regarded Options

Es wurden drei mögliche Strukturen betrachtet:

| Criterion                                | Getrennte Routes und Templates | Gemeinsame Route und gemeinsames Template | Gemeinsame Route mit Untertemplates |
| :--------------------------------------- | :----------------------------- | :---------------------------------------- | :---------------------------------- |
| Doppelter Code                           | Hoch                           | Gering                                    | Mittel                              |
| Rollenabhängige Darstellung              | Klar getrennt                  | Über Jinja-Bedingungen                    | Über getrennte Untertemplates       |
| Zentrale Pflege des Layouts              | Erschwert                      | Einfach                                   | Größtenteils möglich                |
| Implementierungsaufwand                  | Höher                          | Gering bis mittel                         | Mittel                              |
| Geeignet für den aktuellen Projektumfang | Überdimensioniert              | Ja                                        | Möglich                             |
| Spätere Erweiterbarkeit                  | Gut, aber redundant            | Für den aktuellen Umfang ausreichend      | Gut                                 |

### Option 1: Getrennte Routes und Templates

Beispielsweise könnten `/student/dashboard` und `/professor/dashboard` sowie zwei separate HTML-Templates verwendet werden.

Vorteile:

* klare technische Trennung der Rollen,
* weniger Rollenbedingungen innerhalb eines einzelnen Templates,
* jede Oberfläche könnte unabhängig weiterentwickelt werden.

Nachteile:

* Grundstruktur und Layout müssten doppelt gepflegt werden,
* gemeinsame Änderungen müssten in mehreren Dateien vorgenommen werden,
* ähnliche SQLAlchemy-Abfragen und Darstellungslogik würden dupliziert.

### Option 2: Gemeinsame Route und gemeinsames Template

Vorteile:

* zentrale Route,
* gemeinsames Layout,
* weniger doppelter Code,
* einfache Anpassung der gemeinsamen Dashboard-Oberfläche,
* für den aktuellen Projektumfang gut verständlich.

Nachteile:

* Rollenbedingungen in Route und Template erforderlich,
* das Template kann bei vielen weiteren Rollen oder Funktionen unübersichtlich werden.

### Option 3: Gemeinsame Route mit getrennten Untertemplates

Die gemeinsame Route könnte abhängig von der Rolle ein studentisches oder professorales Untertemplate einbinden.

Vorteile:

* gemeinsame Datenvorbereitung,
* stärkere Trennung der rollenabhängigen Darstellung,
* weniger Duplikation als bei vollständig getrennten Dashboards.

Nachteile:

* zusätzliche Dateien und Template-Struktur,
* für den derzeitigen Funktionsumfang mehr Komplexität als notwendig.

Für den aktuellen Umfang wurde die zweite Option gewählt. Sollte das Dashboard später wesentlich umfangreicher werden, kann die rollenabhängige Darstellung in Untertemplates ausgelagert werden, ohne die gemeinsame Route vollständig aufzugeben.
